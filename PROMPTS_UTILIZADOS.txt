1. INTRODUCCION Y METODOLOGIA DE PROMPTING
--------------------------------------------------------------------------------
El presente documento contiene el registro exhaustivo y ordenado de los prompts
utilizados durante el ciclo de vida del proyecto bancario. Para garantizar un
desarrollo robusto, libre de ambiguedades y alineado con los estandares de la
industria y los lineamientos del taller de clase ("Laboratorio Spring Boot con
Cursor 2026"), se empleo un enfoque de "Prompt Engineering" estructurado por
fases incrementales:

- Contextualizacion y Reglas Previas: Definicion del rol, convenciones y stack.
- Especificacion Declarativa: Descripcion precisa de entradas, salidas, tipos,
  reglas de negocio y excepciones esperadas.
- Co-programacion Reactiva e Iterativa: Depuracion guiada de errores de entorno
  (compilacion de modulos Java, pathing, dependencias npm, y codificacion QR).
- Refinamiento de Experiencia de Usuario: Evolucion de una UI basica hacia una
  suite Fintech profesional con graficos, simulador y exportacion de datos.

--- FASE 3: MODELADO DE DATOS (ENTIDADES Y DTOS) ---

PROMPT 3 (Entidades JPA Account y Transaction):
"Crea una entidad JPA Account que represente una cuenta bancaria con los atributos:
id (Long, clave primaria autogenerada), accountNumber (String unico), accountHolder
(String), bankName (String con valor por defecto 'Banco TdeA'), accountType (Enum
con valores SAVINGS y CHECKING), balance (BigDecimal con precision monetaria),
status (Enum con valores ACTIVE, BLOCKED, INACTIVE) y createdAt (LocalDateTime).
Luego crea una entidad JPA Transaction con id, transactionReference (String unico),
sourceAccountNumber, destinationAccountNumber, bankName, amount, description,
timestamp, status (Enum SUCCESS, FAILED, REJECTED), qrCodeData (TEXT) y
qrCodeBase64 (TEXT). Genera constructores, getters, setters y Javadoc en ingles."
-> Componentes generados: Account.java, Transaction.java, AccountType.java,
   AccountStatus.java, TransactionStatus.java.

PROMPT 4 (DTOs con Java Records y Documentacion Swagger):
"Crea los DTOs utilizando Java Records en el paquete com.udea.banktransfer.dto:
1. TransferRequestDTO: con sourceAccountNumber (@NotBlank), destinationAccountNumber
   (@NotBlank), amount (@NotNull, @DecimalMin mayor a cero) y description (@Size max 255).
2. TransferResponseDTO: con id, transactionReference, sourceAccountNumber,
   sourceAccountHolder, destinationAccountNumber, destinationAccountHolder,
   bankName, amount, description, timestamp, status, sourceRemainingBalance,
   qrCodeData, qrCodeBase64 y voucherUrl.
3. AccountResponseDTO: con datos publicos de la cuenta y saldo formateado.
4. ErrorResponseDTO: con timestamp, status (int), error (String), message (String)
   y path (String). Incluye anotaciones @Schema de OpenAPI para documentacion."
-> Componentes generados: TransferRequestDTO.java, TransferResponseDTO.java,
   AccountResponseDTO.java, ErrorResponseDTO.java.


--- FASE 4: REPOSITORIOS, LOGICA DE NEGOCIO Y CODIGO QR ---

PROMPT 5 (Repositorios Spring Data JPA):
"Crea los repositorios Spring Data JPA AccountRepository y TransactionRepository.
AccountRepository debe extender JpaRepository<Account, Long> y proporcionar metodos
derivados para buscar por numero de cuenta: Optional<Account> findByAccountNumber(String num)
y boolean existsByAccountNumber(String num). TransactionRepository debe proporcionar
Optional<Transaction> findByTransactionReference(String ref) y List<Transaction>
findAllByOrderByTimestampDesc(). Anota cada interfaz con Javadoc descriptivo."
-> Componentes generados: AccountRepository.java, TransactionRepository.java.

PROMPT 6 (Servicio Generador de Codigos QR con Google ZXing):
"Crea un servicio en Spring Boot llamado QrCodeService que utilice la libreria
Google ZXing (versiones 3.5.3 de core y javase) para generar codigos QR:
- generateQrCodeImageBytes(String text, int width, int height): retorna byte[]
  con imagen binaria PNG, usando codificacion UTF-8, margen 1 y nivel de correccion
  ErrorCorrectionLevel.H (alto, 30% de redundancia).
- generateQrCodeBase64(String text): retorna un String Data URL en formato
  'data:image/png;base64,...' listo para visualizarse directamente en etiquetas HTML <img>.
Lanza excepciones claras si ocurre algun fallo de codificacion."
-> Componentes generados: QrCodeService.java, integracion pom.xml con com.google.zxing.

PROMPT 7 (Capa de Negocio TransferService con Validaciones Atomicas):
"Crea la interfaz TransferService y su implementacion TransferServiceImpl con
anotacion @Service y @Transactional:
Metodo executeTransfer(TransferRequestDTO request):
1. Validar que la cuenta de origen y de destino no sean iguales.
2. Validar que el monto sea estrictamente mayor a cero.
3. Buscar ambas cuentas; lanzar AccountNotFoundException si no existen.
4. Verificar que ambas cuentas esten en estado ACTIVE; lanzar AccountBlockedException si no.
5. Validar que la cuenta de origen tenga saldo suficiente; lanzar InsufficientFundsException.
6. Descontar el monto del saldo de origen e incrementar en destino de forma atomica.
7. Generar una referencia unica (TXN-timestamp-UUID).
8. Estructurar el payload de datos codificados del comprobante bancario.
9. Invocar QrCodeService para generar la imagen QR en Base64.
10. Persistir la transaccion y retornar el TransferResponseDTO.
Implementa tambien metodos para listar el historico y obtener una transaccion por referencia."
-> Componentes generados: TransferService.java, TransferServiceImpl.java.

PROMPT 8 (Manejo Global de Excepciones HTTP Normalizadas):
"Implementa las excepciones personalizadas de negocio: AccountNotFoundException,
InsufficientFundsException, InvalidTransferException y AccountBlockedException.
Luego crea una clase GlobalExceptionHandler con @RestControllerAdvice que capture
cada una de ellas y genere un ErrorResponseDTO con los codigos HTTP correspondientes:
- 400 Bad Request para InvalidTransferException y errores de validacion @Valid.
- 404 Not Found para AccountNotFoundException.
- 409 Conflict para InsufficientFundsException (saldo insuficiente).
- 403 Forbidden para AccountBlockedException.
- 500 Internal Server Error para excepciones no controladas."
-> Componentes generados: GlobalExceptionHandler.java y excepciones de negocio.


--- FASE 5: CONTROLADORES REST, CORS Y SWAGGER UI ---

PROMPT 9 (Controladores RESTful y Configuracion CORS / Swagger):
"Crea los controladores REST:
1. AccountController (/api/accounts):
   - GET /: lista todas las cuentas bancarias.
   - GET /{accountNumber}: consulta detalles de una cuenta especifica.
2. TransferController (/api/transfers):
   - POST /: procesa una transferencia de dinero (201 Created).
   - GET /: retorna el historico completo de transacciones en orden cronologico.
   - GET /{reference}: consulta una transaccion por codigo de referencia.
   - GET /{id}/qr: retorna los bytes de la imagen PNG del QR (image/png).
Crea una clase CorsConfig para permitir origenes http://localhost:3000 y
http://localhost:5173 con metodos GET, POST, PUT, DELETE, OPTIONS.
Configura SpringDoc OpenAPI con titulo 'Banco TdeA - API de Transferencias'."
-> Componentes generados: AccountController.java, TransferController.java,
   CorsConfig.java, OpenApiConfig.java.

5. Agrega chips de conceptos sugeridos (Matricula TdeA, Arriendo, Honorarios).

5. BUENAS PRACTICAS DE INGENIERIA DE PROMPTS APLICADAS
================================================================================
El exito en la construccion de esta aplicacion bancaria demostro la eficacia de
las siguientes tecnicas de co-programacion asistida por IA:

1. Asignacion de Rol y Directrices Claras:
   Establecer al agente como desarrollador senior FullStack especializado en Spring
   Boot y React con TypeScript, fijando reglas de calidad desde el primer momento.

2. Enfoque Modular y Progresivo:
   No solicitar la aplicacion entera en un unico prompt masivo; en su lugar, se
   avanzo por capas logicas (Base de datos -> Entidades -> DTOs -> Repositorios ->
   Servicios -> Controladores -> Cliente Web -> Pruebas -> Refinamiento UX).

3. Especificacion de Casos Borde y Excepciones:
   Definir con antelacion que ocurriria en situaciones de error (saldo insuficiente,
   mismo origen y destino, cuentas inactivas) permitio generar codigo con manejo de
   excepciones robusto y codigos de estado HTTP estandarizados (400, 403, 404, 409).

4. Trazabilidad y Transparencia:
   Documentar cada prompt y contrastarlo de manera continua contra el enunciado
   oficial del profesor garantizo el cumplimiento del 100% de los requerimientos.
